# Fixture corpus

The fixtures are the behavioural specification of the force model (concept section 4.5). Any implementation, in any language, that produces force states must pass every file here. They are data, not code: nothing in this directory computes anything.

There are two granularities.

- `targeted/` holds hand-written positions with assertions about particular squares, pieces and relations. Each file pins down one rule or fine point. These exist now.
- `snapshots/` holds whole-board force states generated by the reference implementation once the targeted fixtures passed, one complete `force-state.schema.json` document per targeted fixture position, named by the fixture id, to catch regressions everywhere the targeted assertions do not look. They are written by the reference implementation (`FORCE_CORE_UPDATE_SNAPSHOTS=1 cargo test --test snapshots` in `core/`), never by hand.

## Targeted fixture format

One JSON file per position, validating against `../schema/fixture-targeted.schema.json`.

```json
{
  "format": "force-chess/targeted-fixture/0.1",
  "id": "pin-along-file",
  "fen": "4r1k1/8/8/3P4/8/4N3/8/4K3 w - - 0 1",
  "description": "One line on what the position pins down.",
  "decisions": ["Each chess fine point the fixture decides, against the standard rules."],
  "assertions": [
    { "assert": "pin", "pinned": "white knight e3", "pinner": "black rook e8", "king": "e1" },
    { "assert": "attacks", "piece": "white knight e3", "square": "d5", "layer": "L1", "expect": false },
    { "assert": "exclusion", "piece": "white knight e3", "square": "d5", "reason": "pinned", "mentions": ["e8"] }
  ]
}
```

- `fen` is a full FEN so it pastes into any chess tool. The side to move, halfmove clock and fullmove number are ignored: they are not part of the configuration.
- `id` equals the file name without `.json`.
- `decisions` are the chess fine points the fixture settles, written out so they can be read without decoding the assertions. Every fine point is decided against the standard rules of chess and never put to Laurent (concept P7).
- Pieces are named in words: `"white knight f3"`. Squares are `"e4"`. Layers are `"L0"`, `"L1"`, `"L2"`.
- Any assertion may carry a `note`, a plain-words reading for a human. Notes are not checked.

### Assertion kinds

| `assert` | Checks |
|---|---|
| `configuration` | Fields of the configuration record: the canonical string, castling rights, the en passant target. Only the fields given are checked. |
| `attacks` | Whether the piece reaches the square at the layer. At L0: an attack or defence edge exists. At L1: it exists and is legal. At L2: some lookahead entry by the piece reaches the square, that is, lists it among the squares attacked after the move. |
| `attackKind` | The L0 edge exists with the given `kind` (`direct`, `battery`, `xray`, `through_king`), and when given, the `through` square and the exact `path`. |
| `exclusion` | The L0 edge is excluded at L1 with the given reason code, and the explanation text mentions every square in `mentions`. |
| `squareAttackers` | The set of pieces of one colour reaching the square at the layer: `equals` (set equality), `includes`, `excludes`, `count`. At L1 only legal attackers count. At L2 distinct pieces are counted. |
| `control` | The control classification of a square at L0 or L1. |
| `valuation` | The L3 numbers of a square at L0 or L1. Only the fields given are checked. `occupantValue` is not a field of the document: it is read as the value of the square's `occupant` on the document's `valuationScale`, or null when the square is empty, and is the same at every layer. |
| `pin` | The pinned piece carries exactly this pin; `line` when given is the full line from pinner to king. |
| `battery` | A battery with this front and back piece exists; `covered` when given is the exact ordered list of squares reached through the front piece. |
| `xray` | An x-ray from the piece through the enemy piece exists; `beyond` when given is the exact ordered list of squares reached. |
| `pieceConstraint` | The constraints block of a piece: `pinned`, `inCheck`, `noLegalMoves` (a boolean for presence, or a code). |
| `mobility` | The piece's mobility count and, when given, the exact set of `destinations`. |
| `specialMove` | Availability of castling, en passant or promotion for a piece, with the target square and the reason code when given. |
| `lookahead` | After the piece moves to `to`, the squares it attacks directly from there `includes` or `excludes` the ones listed. |
| `sideStatus` | A side's in-check flag, list of checkers, status and legal move count. Only the fields given are checked. |
| `relationCount` | The number of relations of a type, optionally for one colour (the colour of the acting piece). |

## How an implementation runs the corpus

A conforming runner does, for each file in `targeted/`:

1. Parse `fen`, drop the side to move and the clocks, and build the configuration.
2. Compute the force state (a document valid against `../schema/force-state.schema.json`).
3. Evaluate every assertion against that document and report each failure with the fixture id, the assertion, what was expected and what was found.

A runner may be written in the implementation's own language and lives beside it (`core/` for the Rust reference implementation), never here. The assertion semantics above are the whole contract; a runner must not relax them, and must not skip an assertion kind it does not understand.

Snapshots, when they exist, are compared as whole documents: a difference anywhere is a failure, and a changed snapshot is reviewed as a change in behaviour before it is accepted.

## Adding a fixture

Pick one rule or fine point. Build the smallest position that isolates it. Write the decision down in `decisions` before writing assertions. Assert the thing itself and one or two of its consequences on neighbouring records, not the whole board; the whole board belongs to the snapshots. Cross-check the geometry against an independent chess tool before committing. Validate the file against the fixture schema.
